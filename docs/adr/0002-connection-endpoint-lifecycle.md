# ADR-0002: Жизненный цикл Connection и его endpoints

- **Статус:** Accepted
- **Дата:** 2026-11-08

## Контекст

`Computation` является корнем агрегата. `Connection` — вложенная сущность, связывающая клиентскую и провайдерскую Computation для обмена сообщениями. При этом клиентская Computation создаётся раньше провайдерской: на этапе её создания уже появляется liability-переменная, которой необходим стабильный `ConnID`.

Если откладывать создание Connection до появления провайдера или до первого Act, клиентской стороне пришлось бы хранить временную/неполную ссылку либо вводить отдельный этап привязки. Создание второго Connection при появлении провайдера также нарушило бы идентичность канала, уже известную клиенту.

## Решение

Создавать Connection в транзакции создания клиентской Computation — одновременно с её liability-переменной.

Connection хранит endpoints:

- `ClientCompRef` — обязательная ссылка на клиентскую Computation, известную при создании Connection;
- `ProviderCompRef` — nullable-ссылка на провайдерскую Computation, которая добавляется при её создании.

При создании провайдерской Computation система использует `ConnID` из liability-переменной уже существующей клиентской Computation, находит тот же Connection и записывает в него `ProviderCompRef`. Asset-переменная провайдера ссылается на этот же `ConnID`. Новый Connection для этой пары не создаётся.

Оба endpoint должны быть определены до первого Act. Первый Act не создаёт Connection и не выполняет отложенную привязку endpoints.

## Инварианты

- `ConnID` глобально идентифицирует Connection; отдельный составной reference для него не вводится.
- Connection принадлежит агрегату Computation; он не является самостоятельным корнем агрегата.
- `ClientCompRef` обязателен с момента создания Connection.
- `ProviderCompRef` может отсутствовать только в промежутке между созданием клиентской и провайдерской Computation.
- Для одной пары endpoints используется один Connection и один `ConnID`.
- Создание провайдерской стороны и заполнение `ProviderCompRef` выполняются атомарно с созданием провайдерской Computation и её переменных.
- Первый Act допустим только после заполнения обоих endpoints.
- `ChnlID` остаётся отдельной идентичностью interaction channel и не заменяет `ConnID`.

## Последствия

### Положительные

- Клиент получает стабильный `ConnID` сразу при создании своей Computation.
- Обе стороны используют одну запись Connection и одну идентичность канала.
- До первого Act известны обе Computation, поэтому не нужна отложенная привязка.
- Жизненный цикл Connection согласован с тем, что корнем агрегата является Computation.

### Отрицательные

- На коротком этапе между созданием клиента и провайдера Connection существует с незаполненным `ProviderCompRef`.
- Репозитории и ограничения хранения должны явно поддерживать это промежуточное состояние и запрещать запись Act до заполнения обоих endpoints.

## Когда пересмотреть решение

Пересмотреть ADR следует, если изменится порядок создания сторон, появится сценарий, в котором Connection должен существовать без клиентской Computation, либо будет введён отдельный жизненный цикл установления соединения, независимый от создания Computation.
